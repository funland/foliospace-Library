## 原协议提案（历史设计，实际字段以 P1/P2 合约为准）

TV-01 可选新增：

- `GET /api/client/video-works/{workId}/seasons`
- `GET /api/client/video-works/{workId}/episodes?season=1&limit=...&offset=...`
- 季集摘要分开返回本库 availableEpisodeCount、fileCount；只有有来源目录时才给 expectedCount。
  expectedCount 不知道必须 null/缺省，不用0冒充。集下返回版本/文件引用或单独分页入口。
- 继续保留现有 `/video-works/{id}/files`，旧客户端完全不需要知道新的 episodeId。
- 作品已被删除/合并不改变 fileId；旧收藏可继续走原 manifest，详情以可诊断的not-found回退。

TV-03 先写独立协议草案再编码：

- 播放事件字段候选：eventId、sessionId、fileId、episodeId?、positionSeconds、durationSeconds?、
  eventKind、clientSequence、baseRevision；服务器确认用户档案并给 revision/serverUpdatedAt。
- 身份隔离不依赖客户端自行提交任意 profileId；沿用并审计现有鉴权/档案语义。
- 同会话按序、重传幂等；跨设备并发需要明确定义最新有效会话/人工动作优先级，
  不以客户端时钟或“最大进度”粗暴覆盖倒退重看/标未看。
- 暂停/停止/进入后台等关键点提交，播放心跳限频；离线本机继续播放，不等写入成功。
- 视频观看数据与 TMDB 可过期元数据分离；清 provider 缓存不得清观看历史。
- 已新增独立视频同步 API，不复用游戏进度接口，不把旧客户端未上报当作未看。

## 先后顺序与双端门禁

1. **协议冻结**：VID-01/02 示例响应与四组合兼容用例，两端确认；保留旧客户端安装包做回归。
2. **P0 接入**：Docker 测试端提供作品/海报，客户端做新旧自适应与基本作品墙。
3. **P1 剧集整理**：TV-01/02 先提供合成剧集夹具、分页/身份契约，客户端再展示季集计数。
4. **P2 追剧**：TV-03/04 后才宣称跨端继续观看和下一集；TV-05 无外部目录时可独立关闭。
5. **后续想法**：全局时长/画质筛选、更多来源、多集文件等按独立任务评估，不塞入P0必选项。

前后端共享夹具：两部电影（含多版本），一部两季+特别篇剧，重复清晰度/缺图/未匹配，
未播集、编号冲突、同名不同年、跨库同名、双集文件和已人工纠错记录。夹具不能包含
用户凭据、私人影片清单或真实受版权保护的视频内容；用合成媒体即可。

每个编号交付都需记录：server commit/镜像摘要、client commit/build、schema或能力版本、
验证设备和结果、已知限制。编译通过、网页显示、Docker镜像发布、生产替换分别记录。

## Docker 发布与生产保护

- 新字段增量、数据库迁移可重复；videoId/URL不换；schema迁移前做一致性DB+人工图片备份，
  在隔离副本验证恢复，不能只复制活跃 WAL 数据库的主文件。
- 不把 TMDB/其他提供方 key 写入镜像或客户端。Compose默认不开在线匹配；旧配置无需新增必填项。
- NAS浏览不触发解码；沿用已有低并发worker/缓存/超时，新增季集请求不能N+1查全库。
- 不以“未知构建/元数据未匹配/缺集/图片失败”阻止已有文件下载或播放。
- 先18081联调，用户验收后才单独授权18080替换。保留生产特有补丁/挂载/口令/回滚资产。
- 版本号待发布任务确定；GitHub自动化构建、amd64/arm64镜像与Docker Hub标签验证完成后才说发布成功。
- 本计划不授权提交、推送、构建发布、服务重启、真实库批量修正或客户端商店更新。

## 尚待双方选择

- 本轮已采用：自然播放完成或用户明确标已看才发送 completed；服务端不推测95%完成阈值。
  跨设备用 revision 冲突保护，不静默取最大位置；自动连播默认关闭。未来调整需双端回归。
- 旧 thumbnail 正式海报桥接的图像比例兼容方案，以及客户端旧图片缓存刷新办法。
- TV季集DTO/事件DTO最终字段名与能力位；版本推荐信息是否需要服务端补充容器/轨道摘要。
- 更多刮削来源的真实实现与许可边界；不能因有一个本地技能就认定它可直接成为Docker公开服务。
